# 相关论文与开源项目调研

> 调研时间：2026-10-04　|　范围：2024–2026 年（近两年）高相关工作
> 目的：为「数据库助手」项目（面向业务诊断的多轮 SQL 数据分析 Agent）寻找可借鉴的方法与工程基线，支撑差异化魔改。
> Star 数均为调研当日 GitHub API 实测值。

---

## 0. 一句话结论

近两年这条线的研究几乎都收敛到同一个判断：**单次 Text-to-SQL 已到瓶颈，多轮交互 + 执行反馈 + RL 是下一个增长点**。
但现有工作（SQL-Trail、MARS-SQL 等）的**终点都是"生成一条执行正确的 SQL"**（评 BIRD/Spider 执行准确率），
**没有人把"业务根因诊断 + 证据忠实度 + 错误恢复"作为可验证的最终奖励目标**。

这就是你项目最大的差异化空间 —— 你不是要赢 BIRD，而是要证明"3B 模型能在 2×3090 上学会长程诊断决策"。

## 3. 与「数据库助手」方案的差异对照

| 维度 | 现有工作（SQL-Trail / MARS-SQL / DABstep） | 你的方案 | 判断 |
|---|---|---|---|
| 最终目标 | 生成**执行正确的 SQL** | **业务根因结论 + 证据引用** | ✅ 差异化成立 |
| 评测 | BIRD / Spider 执行准确率 | Task Success + Root Cause + Evidence Faithfulness + Recovery | ✅ 更贴近业务 |
| 交互深度 | 固定或自适应轮次 | 最大 8 轮（固定） | ⚠️ 可升级为自适应 |
| 奖励 | 执行正确 + 效率（轨迹级） | 诊断/数值/证据/恢复（轨迹级） | ⚠️ 缺过程奖励 |
| 信用分配 | GiGPO/ARPO 做步级 | GRPO 轨迹级 | ⚠️ 可升级 |
| 语义上下文 | CHESS 分层检索 / WrenAI 语义层 | business_context.json + verified_sql.json | ✅ 思路一致，格式可借工业界 |
| 模型规模 | 7B/14B 为主 | **3B** | ⚠️ 需论证；DeepAnalyze 证明 8B 可行，3B 更难 |
| 交付 | 多数仅开源权重或部分代码 | 计划全链路 Demo | ✅ 可对标 DeepAnalyze 全开源 |

**结论**：你的**任务定义（业务诊断 + 证据化）是真正的新点**；风险集中在**"3B + 多轮 RL + 2×3090"的可行性**，
而 GiGPO / ARPO / RAGEN 恰好是解决这条路上三个核心难题（信用分配 / 采样效率 / 训练崩溃）的现成工具。

## 4. 魔改建议（按优先级）

### P0 — 直接可抄，改动小、收益大

1. **奖励面板加"过程奖励"**
   借 Reasoning-SQL / PaVeRL 的**部分奖励**思想，在现有 4 项终局奖励外，加入"中间发现是否被后续 SQL 复用""是否避免了冗余查询"的轻量过程奖励。
   理由：你的奖励极度稀疏（只有轨迹结束才给分），3B 模型在长轨迹上几乎学不到东西。

2. **固定 8 轮 → 难度自适应轮次预算**
   抄 **SQL-Trail 的 adaptive turn-budget**：按任务难度（预期步骤数）分配 3–10 轮，而不是一律 8 轮。
   理由：既省采样预算，又给"长程能力"留空间。

3. **`business_context.json` 改用工业界语义层 schema**
   借 **WrenAI / SuperSonic** 的指标-维度-同义词-时间口径结构。
   理由：免费获得可解释性和工程可信度，面试加分。

### P1 — 需要读论文后实现，收益显著

4. **GRPO → GiGPO（步级信用分配）**
   你的核心卖点是"长程决策"，但轨迹级奖励无法定位"哪一步决策错了"。GiGPO 用跨轨迹重复状态做 anchor，**免 Critic** 实现步级优势 —— 正好适配 2×3090 无额外价值网络的约束。

5. **课程采样自进化（WebRL）**
   把你方案的"先 3–5 轮标准任务，再 6–10 轮诊断恢复"升级为 **WebRL 式自进化课程**：用失败任务自动生成新任务，优先采样成功率 20%–80% 的任务。

6. **Verifier 引入"轨迹排序"（MARS-SQL）**
   把纯规则的 Verifier 扩展为**对多条候选轨迹做生成式排序**，用 next-token 概率选最优轨迹。

7. **ARPO 式高熵分支采样**
   在工具返回后的高熵位置做分支，**在相同 rollout 预算下拿到更多有效学习信号** —— 直击你"小规模在线采样"的算力边界。

### P2 — 值得预研的风险项

8. **Echo Trap 防御（RAGEN）**：多轮 RL 最常见的崩溃是模型塌缩成重复输出。务必在 P3 阶段先做小规模验证，准备好 KL + SFT 回放（你方案 6.5 已有雏形）。
9. **3B 可行性论证**：建议在 P1 试跑阶段就加一组 **3B vs 7B Prompt Agent** 的对照（你方案 RQ4 已有），如果 3B 明显不行，及早调整为 7B 或缩小领域。
10. **DuckDB 沙箱**：可直接复用 duckdb MCP server 的只读实现，省掉自己写白名单的时间。
