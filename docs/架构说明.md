# 架构说明

> 本文说明 P0 代码骨架的分层、数据流与关键设计决策。
> 与《SQL多轮数据分析Agent技术方案》配套阅读。

## 一、一句话

Agent 拿到一个业务异常现象，在**只读 DuckDB 沙箱**里连续写 SQL，
根据**真实中间结果**动态切换分析分支，最后提交一份**可验证的**根因诊断。

## 二、目录结构

```
src/sqlagent/
  config.py          配置数据类 + YAML 加载（所有可调参数集中于此）
  runner.py          运行时装配（唯一知道所有部件的地方）

  env/               环境层
    sandbox.py       DuckDB 只读沙箱：语句白名单 / 超时中断 / 行数截断
    database.py      CSV → DuckDB 装载；schema 与列画像抽取
    context.py       语义上下文库 + 词法检索（指标口径、已验证 SQL）

  tools/             工具层
    base.py          Tool 抽象 + JSON Schema 生成 + ToolRegistry 分发
    builtin.py       retrieve_context / execute_sql / final_answer

  agent/             Agent 层
    prompt.py        system prompt 构造（表结构进 prompt）
    parser.py        解析 Qwen3.5 原生 <tool_call> 输出
    state.py         Step / Trajectory，所有派生统计
    policy.py        Policy 协议 + ScriptedPolicy / HFPolicy
    loop.py          AgentLoop 主循环

  reward/verifier.py 可验证奖励
  eval/metrics.py    8 个评测指标

scripts/
  prepare_data.py    生成数据 → 建库 → 建上下文 → 生成任务
  run_demo.py        端到端演示

tests/               87 个单元测试
```

## 三、数据流

```
任务(question)
    │
    ▼
PromptBuilder ──► system prompt（角色 + 工作原则 + 预算 + 表结构 DDL）
    │
    ▼
┌─────────────── AgentLoop（最多 max_turns 轮）───────────────┐
│                                                              │
│  Policy.generate(messages, tools)  ──►  模型原始文本          │
│         │                                                    │
│         ▼                                                    │
│  parse_model_output()  ──►  ToolCall                         │
│         │                                                    │
│         ├─ 无工具调用 ──► 提醒重试（有限次）→ 否则终止         │
│         ├─ 超预算     ──► 拦截并回灌提示（不执行）             │
│         ▼                                                    │
│  ToolRegistry.dispatch()  ──►  ToolResult                    │
│         │                                                    │
│         ├─ terminal → 记录 final_answer，结束                 │
│         ▼                                                    │
│  观测文本回灌 messages，进入下一轮                             │
└──────────────────────────────────────────────────────────────┘
    │
    ▼
Trajectory ──┬──► Verifier  ──►  RewardBreakdown（训练信号）
             ├──► evaluate  ──► 8 个评测指标
             └──► JSONL     ──► SFT / RL 训练样本
```

## 四、关键设计决策

### 1. 沙箱三层防护

| 层 | 手段 | 拦截什么 |
|---|---|---|
| 连接层 | `read_only=True` | 所有写操作 |
| 语句层 | 白名单 + 禁关键字 | `DROP` / `ATTACH` / `COPY` 等 |
| 函数层 | 禁函数名单 | `read_csv` / `glob` 等越权读盘 |

关键字检查**先去注释与字符串字面量**再做整词匹配，否则
`WHERE note = 'DROP'` 这类正常查询会被误杀；反过来，
`created_at` 这类列名也不会被 `CREATE` 误伤。这一点有专门的测试覆盖。

超时用 `connection.interrupt()` 实现——DuckDB Python 接口没有原生 query timeout。

### 2. 只有三个工具，且表结构不进工具

技术方案的明确决定：不设独立的 `search_schema` / `describe_tables`。
表结构直接写进 system prompt，列画像走 `retrieve_context`。
理由：小模型在工具数量增加时选择准确率会明显下降，
且表结构是**稳定信息**，每轮都让模型主动查是浪费预算。

### 3. Policy 协议解耦训练框架

`AgentLoop` 只要求 `generate(messages, tools) -> str`。
这样 P3 阶段从 TRL 切到 vLLM 做 rollout 时，**环境代码一行都不用改**。
已经内置两种实现：`ScriptedPolicy`（离线可跑）与 `HFPolicy`（transformers）。

### 4. 上下文里绝不放业务数值

`retrieve_context` 只返回**定义与范式**，不返回任何聚合结果。
否则模型可以直接从上下文抄答案，可验证奖励立刻失效。
这不是洁癖，是奖励有效性的前提。

### 5. 参考答案由参考 SQL 反算，不手写

`prepare_data.py` 在生成任务文件时，是**跑参考 SQL 从真实数据里取值**。
好处：参考答案与数据库永远一致，不会因为人工笔误导致
「模型答对了却拿不到分」的假失败——这种 bug 在训练里极难定位。

### 6. 「错误恢复」必须要求真的修复

最初实现是「上一条 SQL 失败、下一条成功」就算恢复。
测试发现反面案例能靠「先故意写错一条，再写一条能跑的」白拿 0.10 分。

现在要求**修复后的 SQL 与被拒的 SQL 相似度 ≥ 0.40**，
即模型确实在改，而不是换一条不相关的查询绕过。
这个反 gaming 设计有专门的回归测试（`TestRecoveryAntiGaming`）。

### 7. 被预算拦截的调用不算真实 SQL 调用

`n_sql_calls` 只统计**真正到达沙箱**的查询。
否则 SQL 执行率、冗余查询率这些指标会被拦截动作污染。

### 8. 非 ASCII 工具名不能静默丢弃

解析器的函数名正则放宽到「非空白非 `>`」，而不是限制成 ASCII 标识符。
否则模型吐出非法工具名时会被静默丢弃，模型收不到任何反馈、
只能在循环里空转；现在会明确回灌「不存在名为 X 的工具」。

## 五、已验证结论

跑 `python scripts/run_demo.py` 可复现：

| 场景 | 总分 | 说明 |
|---|---|---|
| 正确轨迹 | **+0.9000** | 诊断 0.55 + 数值 0.20 + 证据 0.15；任务成功 |
| 反面轨迹 | **-0.0500** | 非法 SQL -0.03 + 重复查询 -0.02；任务失败 |

差距 0.95，奖励函数具备足够区分度。

测试：`pytest tests -q` → **87 passed**。

## 七、待确认的设计问题

1. **`tool_response_style`**：`structured`（原生 `role="tool"`）与 `text`
   （观测拼进 user 消息）哪种在 Qwen3.5 官方模板下渲染更稳，需实测确认。
2. **LoRA 目标模块**：Qwen3.5 的 delta-net 投影层（`in_proj_qkv` / `in_proj_z` /
   `out_proj`）是否要纳入，需通过消融实验决定。
3. **`final_answer` 的 schema**：目前要求 `key_findings[].evidence_sql`，
   实际模型是否稳定产出这个结构需要验证。
