# sql-diagnosis-agent

> 面向业务诊断的多轮 SQL 数据分析 Agent

围绕高层业务诊断目标，在 DuckDB 环境中连续生成并执行 SQL，**根据真实中间结果动态调整分析分支**，并通过可验证奖励学习错误恢复、停止决策与证据化回答。

当前状态：**P0 代码骨架已完成并跑通**（技术方案见 [`docs/`](docs/)，训练尚未开始）。

---

## 一句话定义

本项目训练一个 4B 级多轮 SQL 数据分析 Agent：它围绕高层业务诊断目标，在 DuckDB 环境中连续生成和执行 SQL，根据真实中间结果动态调整分析分支，并通过可验证奖励学习错误恢复、停止决策和证据化回答。

## 核心设计

| 项目项 | 确定方案 |
|---|---|
| 核心任务 | 目标驱动的业务异常定位与根因诊断 |
| 结构化数据接口 | SQL 统一入口，本地使用 DuckDB（只读沙箱） |
| 辅助语义信息 | 指标定义、数据字典、已验证 SQL 示例（**不含业务数值**） |
| 工具集 | `retrieve_context` / `execute_sql` / `final_answer` |
| 学生模型 | **Qwen3.5-4B**（Apache-2.0，262K 上下文，原生工具调用模板） |
| 训练路线 | API 教师轨迹生成 → 执行验证 → QLoRA SFT → 轻量 GRPO |
| 算力边界 | 1×RTX 4090D 24GB（原方案为 2×RTX 3090）；QLoRA；短轨迹、小规模在线采样 |
| 主要评测 | 诊断成功率、根因准确率、证据忠实度、恢复成功率、调用成本 |

## 快速开始

```bash
# 1. 安装依赖（仅需 duckdb / pandas / pyyaml，无需 GPU）
pip install -e ".[dev]"

# 2. 生成演示数据 → 建库 → 构建语义上下文 → 生成任务
python scripts/prepare_data.py --demo

# 3. 跑一条完整轨迹（离线，不依赖模型）
python scripts/run_demo.py            # 正确轨迹：+0.90
python scripts/run_demo.py --script bad   # 反面轨迹：-0.05

# 4. 跑测试
pytest tests -q                       # 87 passed
```

用真实模型跑（需 GPU 与已下载的权重）：

```bash
python scripts/run_demo.py --model
```

## 实测结论（P0）

| 场景 | 奖励总分 | 说明 |
|---|---|---|
| 正确轨迹 | **+0.9000** | 诊断 0.55 + 关键数值 0.20 + 证据 0.15；任务成功 |
| 反面轨迹 | **-0.0500** | 非法 SQL -0.03 + 重复查询 -0.02；任务失败 |

奖励函数具备 0.95 的区分度。反面轨迹同时验证了反 gaming 设计：
「先故意写错一条再写条对的」无法骗取错误恢复分。

## 为什么不是普通的 Text-to-SQL

| 维度 | 普通 Text-to-SQL | 本项目 |
|---|---|---|
| 输入 | 明确事实问题 + Schema | 高层诊断目标 + 数据库 + 语义上下文 |
| 决策单位 | 一次生成一条 SQL | 每轮选择下一条 SQL 或结束 |
| 环境反馈 | 主要用于最终评测 | 每条 SQL 的结果决定下一步 |
| 计划 | 通常静态或隐式 | 基于中间结果动态更新子目标 |
| 输出 | SQL 或单一答案 | 根因、关键数值、证据引用和建议 |
| 奖励 | 执行正确率 | 最终诊断 + 证据 + 恢复 + 效率 |

**判定边界**：如果一个任务在执行第一条 SQL 前就能确定全部后续查询，它仍然只是固定工作流；只有后续 SQL 的筛选维度、假设或停止条件依赖上一轮结果时，才计入动态多轮任务。

## 相关调研

近两年该方向的工作几乎都收敛到同一判断：**单次 Text-to-SQL 已到瓶颈，多轮交互 + 执行反馈 + RL 是下一个增长点**。
但现有工作（SQL-Trail、MARS-SQL 等）的终点都是「生成一条执行正确的 SQL」，本项目把终点放在「可验证的业务根因结论」上。

详见 [`docs/调研-相关论文与开源项目.md`](docs/调研-相关论文与开源项目.md)。
