# sql-diagnosis-agent

> 面向业务诊断的多轮 SQL 数据分析 Agent

围绕高层业务诊断目标，在 DuckDB 环境中连续生成并执行 SQL，**根据真实中间结果动态调整分析分支**，并通过可验证奖励学习错误恢复、停止决策与证据化回答。

当前状态：**方案阶段**（技术方案见 [`docs/`](docs/)，工程实现尚未开始）。

---

## 一句话定义

本项目训练一个 3B 级多轮 SQL 数据分析 Agent：它围绕高层业务诊断目标，在 DuckDB 环境中连续生成和执行 SQL，根据真实中间结果动态调整分析分支，并通过可验证奖励学习错误恢复、停止决策和证据化回答。

## 核心设计

| 项目项 | 确定方案 |
|---|---|
| 核心任务 | 目标驱动的业务异常定位与根因诊断 |
| 结构化数据接口 | SQL 统一入口，本地使用 DuckDB |
| 辅助语义信息 | 指标定义、数据字典、已验证 SQL 示例 |
| 工具集 | `retrieve_context` / `execute_sql` / `final_answer` |
| 学生模型 | Qwen2.5-3B-Instruct |
| 训练路线 | API 教师轨迹生成 → 执行验证 → QLoRA SFT → 轻量 GRPO |
| 算力边界 | 2×RTX 3090 24GB；QLoRA；短轨迹、小规模在线采样 |
| 主要评测 | 诊断成功率、根因准确率、证据忠实度、恢复成功率、调用成本 |

## 为什么不是普通的 Text-to-SQL

| 维度 | 普通 Text-to-SQL | 本项目 |
|---|---|---|
| 输入 | 明确事实问题 + Schema | 高层诊断目标 + 数据库 + 语义上下文 |
| 决策单位 | 一次生成一条 SQL | 每轮选择下一条 SQL 或结束 |
| 环境反馈 | 主要用于最终评测 | 每条 SQL 的结果决定下一步 |
| 计划 | 通常静态或隐式 | 基于中间结果动态更新子目标 |
| 输出 | SQL 或单一答案 | 根因、关键数值、证据引用和建议 |
| 奖励 | 执行正确率 | 最终诊断 + 证据 + 恢复 + 效率 |

**判定边界**：如果一个任务在执行第一条 SQL 前就能确定全部后续查询，它仍然只是固定工作流；只有后续 SQL 的筛选维度、假设或停止条件依赖上一轮结果时，才计入动态多轮任务。

## 路线图

| 阶段 | 周期 | 主要工作 | 验收标准 |
|---|---|---|---|
| P0 环境 | 第 1 周 | DuckDB 导入、SQL 沙箱、轨迹记录 | 可复现执行并回放一条任务 |
| P1 数据试跑 | 第 2–3 周 | 转换 100 任务，生成 300–500 轨迹 | 自动执行通过率 ≥70%，人工审查机制可用 |
| P2 SFT | 第 4–5 周 | 清洗 1,500–3,000 轨迹，QLoRA 训练 | 工具格式正确率 ≥95%，显著优于 Prompt Agent |
| P3 RL | 第 6–7 周 | 接入 GRPO，完成 1,200–2,000 rollout | 恢复/长任务指标提升且基础 SQL 不退化 |
| P4 实验 | 第 8–9 周 | 主对照、消融、误差分析 | 结果可重复，结论能对应 RQ |
| P5 Demo | 第 10 周 | 交互界面、轨迹可视化、项目文档 | 可展示动态分支和错误恢复案例 |

## 相关调研

近两年该方向的工作几乎都收敛到同一判断：**单次 Text-to-SQL 已到瓶颈，多轮交互 + 执行反馈 + RL 是下一个增长点**。
但现有工作（SQL-Trail、MARS-SQL 等）的终点都是「生成一条执行正确的 SQL」，本项目把终点放在「可验证的业务根因结论」上。

详见 [`docs/调研-相关论文与开源项目.md`](docs/调研-相关论文与开源项目.md)。
